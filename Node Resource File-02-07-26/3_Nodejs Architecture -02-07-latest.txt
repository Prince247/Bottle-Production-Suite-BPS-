Difference Between Synchronous code Vs Asynchronous code

Synchronous code executes one operation at a time and waits for it to finish before moving to the next operation. 
It blocks the execution thread.

Asynchronous code starts an operation and doesn't wait for it to finish. Node.js can continue executing other code or operation and 
handle the result later using callbacks, promises, or async/await.

---------------------------------------
example
Synchronous:

const data = fs.readFileSync('file.txt');
console.log(data);
console.log('Done');

Here, Node.js waits for the file to be completely read before printing "Done"

Asynchronous:
fs.readFile('file.txt', (err, data) => {
    console.log(data);
});
console.log('Done');
Here, "Done" can print before the file reading finishes.

✔️ Very short interview version
Node.js is a run time environment & is single-threaded for JavaScript execution, but internally it uses libuv, thread pool for certain operations, 
allowing it to handle multiple requests concurrently without blocking the main JavaScript thread.


✔️ How Nodejs Works?
-> Node.js is a runtime that uses the V8 engine to execute JavaScript code. 
When a request comes to a Node.js server, If the code is a normal synchronous operation, V8 executes it directly on the Call Stack. once 
it done 2nd priority is Process.nextTick() But if the code performs an asynchronous operation such as reading a file system, doing certain cryptographic work, compression, or some DNS operations, 
Node.js uses libuv to handle that operation without blocking the main JS thread.
libuv uses Thread Pool. The Thread Pool has a default size of 4 threads and can be increased using UV_THREADPOOL_SIZE up to 128. 
While that asynchronous operation is running, Node.js can continue executing other JavaScript code instead of waiting for it. 
Once the asynchronous operation finishes, its callback is made ready to be executed and is placed into the appropriate queue. 
This is where the Event Loop becomes important: the Event Loop continuously checks whether the Call Stack is empty
When the Call Stack is empty, it takes micro & macro task execute through V8. This is how Node.js can handle many concurrent requests even though JavaScript itself runs on a single main thread.

process.nextTick() puts the function into Node's special nextTick queue.

process.nextTick(() => {

2. process.nextTick() registers its callback in the Next Tick Queue.
3. V8 executes console.log('End').
4. Synchronous execution finishes.
5. Node.js processes the Next Tick Queue.
6. V8 executes the nextTick callback.

-------------------------About JSON----------------------------------------------------------
1) JSON.parse() is synchronous and blocks the main thread until parsing finishes, even if the file was read asynchronously using fs.readFile().
2) JSON parsing happens on a separate thread without blocking the main thread. Once completed, the result is sent through postMessage(), and the main thread handles it through the message event.Main Thread

---------------------------------Who use ThreadPool Worker Thread------------------------------------------------------------
Asynchronous Network I/O means Node.js sends a request over the network and doesn't wait by blocking the main thread for the response.

For example, when you call an API using Axios:
1. Node.js sends the HTTP request.
2. It continues executing other tasks instead of waiting.
3. When the API response arrives, Node.js processes the response through the event loop

HTTP API calls (Fetch, Axios): Neither libuv thread pool nor Worker Threads. They use asynchronous network I/O.
Database calls (Sequelize, PostgreSQL): Neither. They use asynchronous network I/O.
File system APIs (fs.readFile): Generally use the libuv thread pool.
CPU-intensive JavaScript: Main thread by default; use Worker Threads to offload it.
JSON parsing (JSON.parse): Main thread; synchronous execution.
Crypto (crypto.pbkdf2): Generally uses the libuv thread pool.
DNS (dns.lookup): Uses the libuv thread pool.
Timers (setTimeout): Managed by the event loop, not the thread pool.

✔️ EventEmitter is basically a synchronous event mechanism that runs on the main JavaScript thread
const EventEmitter = require('events');
const emitter = new EventEmitter();
emitter.on('hello', () => {
    console.log('Listener 1');
});
emitter.on('hello', () => {
    console.log('Listener 2');
});
emitter.on('hello', () => {
    console.log('Listener 3');
});
emitter.emit('hello');
console.log('Done');

Execution is:
emit('hello')
      ↓
Listener 1
      ↓
Listener 2
      ↓
Listener 3
      ↓
Done

When emitter.emit('hello') is executed, all listeners registered for the hello event are executed synchronously, 
one after another, on the main JavaScript thread. If any listener performs blocking work, it blocks the main thread, 
so other JavaScript callbacks cannot execute until that work finishes.
